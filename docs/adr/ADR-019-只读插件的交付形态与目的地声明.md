# ADR-019：只读插件的交付形态与目的地声明

- 状态：Accepted，用户于 2026-10-07 批准。
- 日期：2026-10-07

## 背景

[ADR-013](ADR-013-Agent运行时集成边界.md) 定了依赖方向：运行时专用的插件放在运行时自己的仓库。首个垂直切片据此落地——一个只读插件把五个查询命令暴露为 Harness 工具，实现位置与验收见 [接口说明](../harness-interface.md#harness-侧实现)。

实现过程中有两个选择被确定下来，它们都不从 ADR-013 直接推出，且每次改动插件都会重新遇到：插件以什么形态交付给运行时；以及 `destination` 由谁决定——它直接决定 Lifebase 放不放行，而模型路由在 Harness 侧。

## 决策

### 1. 零构建纯 ESM 包，且刻意留在 pnpm workspace 之外

插件是直接运行的纯 ESM JavaScript：没有编译步骤，没有构建产物，没有 install script。它交给运行时的只有 `package.json` 的 `dsh.bundle.patch` 判据加一份 patch 层。它也不加入 fork 的 pnpm workspace（`pnpm-workspace.yaml` 的 glob 不覆盖 `plugins/`），因此不进入 fork 的 tsconfig、lint 与目录门禁。

bare import 依赖 `peerDependencies` 声明：被 link 进 profile 的插件，只有把包名写进自己的 peer 名单，Harness 才把它路由到自己的副本。这三个包在 fork 根目录的 `node_modules/` 里并不存在，因此这不是版本偏好问题，而是能否解析的问题。

理由是插件是转接层，不是产品代码：它做的事是把参数数组交给 CLI、把 CLI 的 v1 信封原样返回，自身不含需要类型系统守护的逻辑。进入 fork 的构建图会让它随 fork 的 TypeScript 配置、lint 契约与发布流程一起变，而它需要的是改一行就能重跑。

### 2. `destination` 只声明，不自动推断

插件把配置里的 `destination` 原样传给 `--destination`，不检查模型路由，也不尝试猜测。门禁在 Lifebase 侧执行。

插件默认 `cloud`，CLI 默认 `local`，两者不同是刻意的。`destination` 是「这批数据会去哪里」的声明，而声明失准的两个方向后果不对称：声明得比实际更暴露，只会让门禁更严；声明得比实际更宽松，才会让数据在门禁放行后流向云端。默认因此取严格一侧，而不是跟随 CLI 面向终端读者的 `local`。

代价是正确性无法机械校验：切换模型路由必须同时改配置并重新跑一次查询确认，这条只写在 README 与接口文档里。

## 被否方案

- **加入 workspace 并写成 TypeScript**：换来类型检查，代价是插件随 fork 的构建配置漂移，且无法在不动 Harness 版本的情况下单独修改。
- **让插件自带这三个依赖**：解析不到宿主的注册表实例，工具注册与调度会分裂成两套。
- **由插件探测模型路由自动填 `destination`**：一次会话里模型可以切换（子 agent、不同 profile），插件拿不到稳定的路由身份；猜错的方向恰好是宽松的那一侧，等于绕过门禁。
- **默认 `local`**：未配置时所有云端模型一律失败，插件的存在意义被取消，且失败模式从「配置没填」退化成「看起来能用但一直 EGRESS_BLOCKED」。
- **让 Lifebase 自己读实际路由**：把运行时的实现细节变成数据层的依赖，与 ADR-013 决策 2 相悖。

## 后果

- 收益：插件不随 fork 的构建体系变化；信封原样透传，契约只有 Lifebase 一处，不产生第二份会漂移的类型定义。
- 代价：插件没有类型检查与 lint 覆盖，正确性依赖端到端验收与信封透传；不能以 PR 形式回上游（上游也不收外部 PR）；`destination` 与真实路由的一致性只能人工核对。
- 本 ADR 无机械门禁。插件形态由端到端验收间接覆盖，`destination` 的诚实性没有门禁。
